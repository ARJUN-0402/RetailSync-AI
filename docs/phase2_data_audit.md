#### Data Generation Logic

**Sales Generation (lines 64-88):**
```python
for date in dates:
    for store_id in stores["store_id"]:
        n_products = np.random.randint(5, 15)  # Random 5-15 products per store per day
        sampled_products = np.random.choice(
            products["product_id"], n_products, replace=False
        )
        for product_id in sampled_products:
            base_demand = np.random.randint(1, 20)
            seasonal_factor = (
                1.3
                if Electronics and Nov - Dec
                else 1.2
                if Clothing and summer
                else 1.0
            )
            trend_factor = 1 + (date - start_date).days / (DAYS * 2)
            quantity = max(
                0, int(np.random.poisson(base_demand * seasonal_factor * trend_factor))
            )
```

**Issues:**
1. **No explicit demand simulation**: Sales are generated by randomly sampling products, not by simulating customer demand. This is why zero-inflation exists — products simply aren't selected on most days.
2. **Seasonality is applied but too weak**: The seasonal multipliers (1.3x for Electronics, 1.2x for Clothing) are applied to random base demands (1-20), making the seasonal effect statistically invisible in aggregates.
3. **Trend factor is minimal**: `1 + days/1460` ranges from 1.0 to 2.0 over 2 years, but since base_demand is random, the trend is barely perceptible.

**Inventory Generation (lines 90-107):**
```python
for date in inventory_dates:  # Weekly (every 7 days)
    for store_id in stores["store_id"]:
        for product_id in products["product_id"]:
            base_stock = np.random.randint(20, 200)
            quantity_on_hand = np.random.randint(0, base_stock)
            reorder_point = np.random.randint(10, 50)
            max_stock_level = base_stock
            warehouse_id = np.random.choice(warehouses["warehouse_id"])
```

**Issues:**
1. **No demand-inventory correlation**: Inventory levels are completely random, unrelated to actual sales patterns.
2. **No lead time integration**: `reorder_point` is random (10-50), not calculated based on `lead_time_days` or demand variability.
3. **No stockout modeling**: Stockouts emerge purely from random chance (1.26% weekly rate).
4. **Random warehouse assignment**: `warehouse_id` is randomly assigned per product-store, not based on geography, capacity, or supplier relationships.

## 3. Zero-Inflation Analysis

### README Claim
> "Zero-inflation: ~81% of daily demand values are zero"

### Verification

| Source | Zero Demand | Non-Zero Demand | Zero % |
|--------|-------------|-----------------|--------|
| Raw sales CSV | 1,400 | 67,816 | 2.02% |
| Feature daily CSV | 297,184 | 67,816 | 81.42% |

### Root Cause

The 81% zero-inflation in `features_daily.csv` is an **artifact of the data generation method**, not realistic retail behavior:

1. Sales are generated by randomly sampling 5-15 products per store per day
2. Each product appears in only ~10% of daily store records
3. Feature engineering creates a **complete daily grid** (500 product-store combos × 730 days = 365,000 rows)
4. Missing days are filled with 0, creating artificial zero-inflation

### Assessment

- The zero-inflation is **real in the feature dataset** but **not realistic**
- In real retail, a product might have zero demand on a given day, but not because it was "not sampled"
- The Poisson distribution with `base_demand * seasonal_factor * trend_factor` would produce more realistic demand patterns if simulated for all product-store combinations daily

### Impact on Forecasting

The extreme zero-inflation (81%) makes forecasting extremely difficult:
- Most ML models struggle with sparse data
- Baseline mean wins because it's robust to zeros
- sMAPE becomes meaningless (185% reported)
- The project correctly identifies this limitation

## 4. Seasonality Analysis

### README Claim
> "Seasonality: Electronics peaks in Nov-Dec, Clothing peaks in summer"

### Verification

#### Electronics Monthly Distribution

| Month | % of Sales | Expected if Uniform |
|-------|------------|---------------------|
| Nov | 8.2% | 8.3% |
| Dec | 8.4% | 8.3% |
| **Nov+Dec Total** | **16.5%** | **16.7%** |

#### Clothing Monthly Distribution

| Month | % of Sales | Expected if Uniform |
|-------|------------|---------------------|
| Jun | 8.3% | 8.3% |
| Jul | 8.5% | 8.3% |
| Aug | 8.1% | 8.3% |
| **Jun+Jul+Aug Total** | **24.8%** | **25.0%** |

### Conclusion

**Seasonality is NOT present in the data.** The seasonal factors in `generate_dataset.py` are mathematically present but statistically swamped by:
1. Random base_demand (1-20)
2. Random product sampling (5-15 per store per day)
3. Poisson noise

The effect size (1.2x-1.3x) is too small relative to the random variation to be detectable in aggregates.

### Impact

- Forecasting models cannot learn seasonal patterns because they don't exist in the data
- The README claim is **misleading** — it describes intended behavior, not actual behavior
- Any seasonal features in the model are effectively noise

## 5. Stockout Analysis

### README Claim
> "Stockouts: 36.6% of product-store combinations experience stockouts"

### Verification

| Metric | Value | Source |
|--------|-------|--------|
| Product-store combos that ever had stockout | 74.8% | Full history analysis |
| Weekly average stockout rate | 1.26% | Per-week analysis |
| Max weekly stockout rate | 2.60% | Per-week analysis |
| Current stockout HIGH (latest date) | 3.2% | Inventory intelligence |
| Current stockout MEDIUM (latest date) | 33.8% | Inventory intelligence |

### Conclusion

The README claim of **36.6% is incorrect**. The actual values are:
- **74.8%** of product-store combinations experience stockouts at some point during the 2-year period
- **1.26%** average weekly stockout rate
- **3.2%** are currently at HIGH risk

The README appears to have mixed up different metrics or used a stale calculation.

### Root Cause

Stockouts in the synthetic data are **purely random**:
- `quantity_on_hand = np.random.randint(0, base_stock)` where `base_stock = np.random.randint(20, 200)`
- No correlation with demand, lead time, or seasonality
- ~1.26% chance of stockout per product-store per week

This makes inventory risk detection less meaningful because stockouts are not driven by realistic supply-demand dynamics.

## 8. Data Realism Assessment

### Strengths

1. **Reproducible**: Seed=42 ensures consistent outputs
2. **Clean**: No missing values, no duplicates, proper dates
3. **Volume**: 69K sales, 52.5K inventory, 365K features — sufficient for ML
4. **Foreign keys**: All relationships intact in database
5. **No data leakage in generation**: Raw data is generated before any modeling

### Weaknesses

1. **Zero-inflation is artificial**: Caused by sampling method, not realistic demand patterns
2. **No seasonality**: Seasonal factors are present but too weak to detect
3. **No demand-inventory correlation**: Inventory is random, not driven by sales
4. **No supplier logic**: Lead times and reliability scores are generated but never used
5. **No stockout modeling**: Stockouts are random, not demand-driven
6. **No product lifecycle**: Launch dates exist but don't affect demand
7. **No store-type effects**: Urban/suburban/rural stores have identical demand distributions
8. **No promotion effectiveness**: Promotions are random, don't affect demand

### Portfolio Suitability

For a **portfolio project**, the current data is **acceptable but not impressive**. It demonstrates:
- Data generation skills
- Pipeline construction
- Feature engineering
- ML modeling

But it lacks the **realism** that would make it stand out to a technical reviewer. A recruiter or ML engineer would notice:
- The weak seasonality
- The artificial zero-inflation
- The random inventory logic
- The incorrect README claims

## 10. Recommendations

### Critical (Fix Before Portfolio)

1. **Correct README stockout claim**: Change "36.6%" to actual value or remove
2. **Document seasonality limitation**: Explain that seasonal effects are present in code but weak in data
3. **Document zero-inflation cause**: Explain it's an artifact of the sampling method

### High Priority (Improve Data Realism)

4. **Generate demand for ALL product-store combinations daily**: Instead of random sampling, simulate Poisson demand for every combination
5. **Link inventory to demand**: Make `quantity_on_hand` correlated with recent sales
6. **Link reorder points to demand**: `reorder_point = lead_time_days * avg_demand + safety_stock`
7. **Model stockouts explicitly**: Reduce `quantity_on_hand` when demand exceeds stock
8. **Strengthen seasonality**: Increase seasonal multipliers or add category-specific effects

### Medium Priority

9. **Add store-type effects**: Urban stores should have higher baseline demand
10. **Add promotion effectiveness**: Promotions should increase demand, not just be random flags
11. **Add supplier reliability effects**: Less reliable suppliers should have higher stockout risk
12. **Add product lifecycle**: New products should have ramping demand

### Low Priority

13. **Add data quality report**: Output a summary of data generation statistics
14. **Add data lineage**: Track which scripts produced which outputs
15. **Parameterize generation**: Move constants to config file
